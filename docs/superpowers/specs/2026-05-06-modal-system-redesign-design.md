# 全局弹窗系统重设计方案

## 背景

当前项目中的弹窗容器主要分布在以下体系中：

- `AlertDialog`：用于确认、危险操作、关闭提醒等
- `Sheet`：用于移动端导航、侧边设置入口等
- 业务层直接使用的弹窗容器样式：在具体面板内自行附加 `max-w-*`、`p-*`、标题和按钮布局规则

现状问题不是单个弹窗“丑”，而是整套比例系统缺失，导致：

1. 同类弹窗尺寸不一致
2. 长标题或长名称会把弹窗横向撑坏
3. 表单型弹窗宽窄随页面临时 class 漂移
4. 内容多时经常整体过高，而不是内容区滚动
5. `Sheet` 宽度过于随意，与桌面/移动场景不协调
6. 各弹窗虽然基本复用全局 token，但没有形成统一的主题化布局规范

用户希望“全面重做”，同时明确要求：

- 与全局样式主题保持一致
- 不是局部修补，而是系统性调整

## 目标

建立一套与现有全局主题一致的弹窗系统规范，并逐步替换当前散落的尺寸与布局写法。第一阶段的目标为：

1. 为 `AlertDialog`、`Sheet` 和现有业务弹窗容器建立统一的尺寸层级
2. 统一头部、内容区、底部操作区的布局规则
3. 统一滚动行为，避免整体高度失衡
4. 统一危险确认、表单录入、信息展示、工作台侧板四类弹窗的比例策略
5. 保持现有主题 token、颜色、边框、阴影、按钮风格不变，不新造一套视觉系统

## 非目标

本次不包含：

- 不改业务流程逻辑
- 不新增新的主题 token
- 不重写所有业务内容结构
- 不引入新的第三方弹窗库
- 不重做浮层动画体系，只做必要收口

## 方案选择

### 方案 1：建立统一弹窗设计系统并逐步接入（采用）

先定义弹窗分类、尺寸层级、布局规范和主题约束，再让现有弹窗按类型接入统一容器或统一样式能力。

优点：

- 能从根本解决“比例不协调”问题
- 后续新增弹窗有明确标准
- 可分阶段落地，不需要一次性重写所有业务

缺点：

- 需要先做规范抽象，而不是直接修单个弹窗

### 方案 2：逐个业务弹窗修补

不采用。虽然短期可见，但无法保证一致性，后续仍会继续失衡。

### 方案 3：只调整基础组件默认宽度

不采用。只改默认 `max-w` 无法覆盖确认型、表单型、工作台型在头部、内容区、滚动区的差异需求。

## 设计原则

### 1. 与全局主题一致

弹窗系统必须严格复用现有视觉语言：

- 背景层级继续使用现有 `bg-background-*`
- 边框继续使用 `border-border-*`
- 标题/正文/弱文本继续使用现有 `text-text-*`
- 阴影沿用现有 elevated surface 风格
- 按钮继续复用项目现有 `buttonVariants`

本次只统一比例、间距、布局和结构节奏，不引入新的色彩体系或独立弹窗主题。

### 2. 标题不承载长动态文本

所有长名称、长标识符、长路径、长描述信息都应进入内容区，不应直接拼进标题。标题负责表达动作或状态，动态长文本作为正文中的独立块展示。

### 3. 弹窗整体稳定，内容区承担滚动

弹窗外壳不应因内容变多而无限增高。对于长表单、长说明、长列表，统一采用：

- 标题区固定
- 内容区滚动
- 底部操作区固定

### 4. 同类弹窗使用同一比例体系

不能再由业务页面自由决定 `max-w-md` / `max-w-xl` / `w-56`。尺寸应由弹窗类型和尺寸枚举决定。

## 弹窗分型

### A. 确认型弹窗

适用场景：

- 删除确认
- 放弃修改
- 危险操作二次确认

推荐容器：`AlertDialog`

设计规则：

- 默认宽度：`max-w-md`
- 内容密度较紧凑
- 标题短句化
- 正文最多承载 2 到 4 行核心说明
- 长对象名放正文中的独立块，不进入标题
- 操作区右对齐，取消在左，主动作在右，危险按钮最右

### B. 表单型弹窗

适用场景：

- 新建服务商
- 编辑配置
- 参数录入

推荐容器：统一弹窗内容容器

设计规则：

- 默认宽度：`max-w-2xl`
- 最大高度：`min(80vh, 900px)` 语义
- 内容区允许滚动
- 单列为默认，信息密度高时可响应式双列
- 头部和底部固定，不随内容滚动

### C. 信息型弹窗

适用场景：

- 说明弹窗
- 结果展示
- 状态详情
- 日志、长文本、列表预览

设计规则：

- 默认宽度：`max-w-3xl`
- 大内容场景必须使用独立滚动内容区
- 正文区可以容纳代码块、列表、说明块，但不挤压标题区和按钮区

### D. 工作台型侧板

适用场景：

- 设置导航侧板
- 辅助编辑侧板
- 工具配置抽屉

推荐容器：`Sheet`

尺寸档位：

- `sm`: 420px
- `md`: 560px
- `lg`: 720px

规则：

- 移动端导航类默认 `sm`
- 设置或编辑类默认 `md`
- 只有复杂工作流或多段编辑区才使用 `lg`
- 不再继续使用 `w-56` 或 `w-3/4 + sm:max-w-sm` 这种混合且不可预测的策略作为业务默认值

## 布局规范

### 1. 头部

统一要求：

- 标题与描述使用稳定的垂直节奏
- 标题字号和字重统一
- 描述文本不承担主要结构排版职责
- 如有状态标签或辅助说明，应放在标题区下方，不改变整体层级

### 2. 内容区

统一要求：

- 采用明确的 `space-y-*` 节奏
- 表单项之间间距一致
- 内容块之间以 section/card 组织，而不是靠多个随机 margin 堆叠
- 长文本与长标识符使用包裹块展示，避免拉伸容器

### 3. 底部操作区

统一要求：

- 主操作位于最右
- 次要操作位于主操作左侧
- 危险操作仍遵循现有 danger 视觉，但按钮区整体节奏统一
- 移动端允许纵向堆叠，桌面端以右对齐横向排列为主

### 4. 滚动行为

统一要求：

- 外层容器尽量不滚动
- 长内容仅在内容区滚动
- 顶部和底部区域保持可见

## 组件层设计

为避免业务侧继续散落硬编码尺寸，本次设计建议新增一层统一封装，而不是要求业务层自己拼 class。

建议新增以下组件：

- `AppAlertDialogContent`
- `AppSheetContent`
- 如后续引入标准 `Dialog`，再补 `AppDialogContent`

这些封装负责：

- 统一尺寸枚举
- 统一最大高度与滚动策略
- 统一头部/内容区/底部区布局骨架
- 继续透传 `className` 作为增量扩展，而不是作为主要布局来源

### 尺寸枚举建议

#### AlertDialog

- `confirm`: `max-w-md`
- `compact`: `max-w-sm`

默认使用 `confirm`

#### Sheet

- `sm`: `w-[420px] max-w-[calc(100vw-1rem)]`
- `md`: `w-[560px] max-w-[calc(100vw-1rem)]`
- `lg`: `w-[720px] max-w-[calc(100vw-1rem)]`

### 结构能力建议

封装后的组件支持：

- `size`
- `contentScrollable`
- `stickyFooter`
- `stickyHeader`

第一阶段至少要支持尺寸与滚动策略，sticky 能力可以以内置 class 先落地，不必过度设计成复杂 API。

## 第一阶段接入范围

### 1. `AlertDialog` 体系

重点收口：

- [ProvidersSettingsPanel.tsx](src/components/Settings/ProvidersSettingsPanel.tsx) 的删除确认弹窗
- [SettingsShell.tsx](src/components/Settings/SettingsShell.tsx) 的关闭未保存确认弹窗

### 2. `Sheet` 体系

重点收口：

- [SettingsShell.tsx](src/components/Settings/SettingsShell.tsx) 的移动端菜单侧板
- 项目中其余 `SheetContent` 使用点统一迁移到尺寸枚举体系

### 3. 后续业务弹窗扩展位

当前仓库未发现统一封装的 `Dialog` 基础组件文件。后续若项目中新增标准 `Dialog`，应直接接入同一套 modal system 规范，而不是重新定义样式。

## 主题一致性要求

为了满足“与全局样式主题保持一致”，实施时必须满足：

1. 不新增独立 modal palette
2. 不为弹窗单独定义与全局冲突的圆角、边框、阴影体系
3. 不改变现有按钮主次关系与 danger 语义
4. 不使用硬编码高对比背景去替代已有 surface token
5. 新增封装组件仍基于当前 UI primitives 构建

## 验收标准

完成后应满足：

1. 同类弹窗尺寸一致，不再出现明显忽宽忽窄
2. 长名称不再撑坏确认弹窗标题
3. 弹窗头部、内容区、底部的间距与层次统一
4. 大内容弹窗不会整体过高，滚动集中在内容区
5. `Sheet` 在桌面与移动端都保持稳定比例
6. 弹窗观感与全局主题保持一致，不显得像另一套系统
7. 前端构建通过

## 后续阶段

第一阶段完成后，如仍需继续优化，可进入第二阶段：

- 为表单型弹窗补统一 `Dialog` 容器
- 为常见弹窗提供标准 section 结构
- 补充设计快照或视觉回归检查

这些不纳入本次实现范围。
